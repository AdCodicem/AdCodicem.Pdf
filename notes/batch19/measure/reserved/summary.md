## Questions

### Q221-1 (#221)
How does the reader read a cross-reference stream row of a reserved type (past 2, including a type field wider than 8 bytes whose excess bytes are not all zero)?

- [R] (a) As ISO 32000-1 7.5.8.3 reads it: a reference to the null object, the row indexed as a free entry so that no older section's row stands for the object: Behavior: X09, X09n, X09w, X09w8, X09d, X09m read null where main serves the older (or the second subsection's) definition; X04/X01/X04w unchanged (null). Index: XRefEntry.Free — GetObject null, GetPresence Missing, no rebuild; ObjectCount/ObjectNumbers count the number as they count free rows (PdfDocument docs gain 'or give a row of a reserved type'); reserved rows take index entries under MaxIndexEntries as free rows do (8M rows reach limit.index-entries, allocation unchanged); a rebuild brings an older body back as for any freed object. RetakeDeferred: taken = true. Tests: 8 change meaning (3 Index.Count +2, the deferred-length row test inverts, a guard twin gains file.root-invalid, 3 HostileInput fixtures need another way to unlist an object). Docs: threat model :421/:422/:424/:445, validation-rules.md :54, lazy-reading.md. Corpus: nothing moves. Cost: two lines in the reader plus fixtures.
- (b) Skipped as today, an older section's row standing; reported: No behavior change; the comment (PdfFileReader.cs:5310, :4463), the threat model and the rules page stop claiming the specification and say the reader departs from it. Under ADR 45 the superseded case (an older row stands: the reader serves what the update replaced) is an Error and the other a Warning — two rules, the split needing a set of skipped numbers bounded by the index guard, checked after the chain (see Q221-4). Matches libqpdf >= 12.3.0, MuPDF and pypdf (non-strict); a full rewrite would later write the superseded revision as current, reported only by this report.

Why: ISO names the reading — null — and never says ignore; the readers we compare with split four ways (skip: libqpdf >= 12.3, MuPDF, pypdf; rebuild: qpdf <= 12.2, pdf.js, Ghostscript; type 2: PDFBox; refuse: poppler), none reads null, so no reader is a reference to follow; under (a) the reader reads the file as the specification says, so ADR 45 makes the finding a plain Warning, one rule; the reader never serves a revision an update superseded (invariant 7); invariant 12 is not at stake (only types 0–2 are allowed in PDF 1.5–1.7, so no valid file holds the row, and ISO's null is the degradation it prescribes for a later type); the corpus holds no such row (403 documents, three independent counts).

### Q221-2 (#221)
Who reports a row of a reserved type: the reader, the validator, or both?

- [R] Both: a reader diagnostic once per section (first row named, others counted) and a validator finding at the section: Invariant 5 satisfied; the same pair shape as xref.section-unreadable/xref.section-malformed and xref.section-missing/xref.section-not-found; consistent with batch 5's settlement that refused rows get their reader report with #210 in this batch (one hook in TryReadXRefChain for both, see the partial lens). ~44 tests whose fixtures write reserved types incidentally must expect or exclude the diagnostic. Docs: diagnostics.md and validation-rules.md rows.
- The validator only: No reader code; a caller who does not validate never learns that an object reads null (a) or from an older revision (b); fewer test changes (only those asserting no finding: 2).
- The reader only: No rule; the validator's report misses a fault the reader saw; the issue's 'Tests in CrossReferenceRuleTests' would assert diagnostics only.

Why: Invariant 5 asks that what the reader meets go to PdfDiagnostics, and every other fault of the chain is reported both ways; the refused rows of #210, decided in this batch, take the same form.

### Q221-3 (#221)
Under which codes (no rule identifier may be a diagnostic code)?

- [R] New codes: diagnostic xref.entry-reserved, rule xref.entry-type-reserved: One new PdfDiagnosticCodes constant and one PdfValidationRuleIds constant, a ReservedTypeRule after xref.section-malformed in the structural profile (its RuleIds listing and the docs table change), manifest.schema.json's two enumerations; the fault named for what it is — neither a malformation (ISO defines its reading) nor a section read in part.
- Folded into existing codes: the diagnostic into the code #210 settles for a section read in part (the partial lens prototypes xref.section-incomplete), the finding into xref.section-malformed: No new code; but xref.section-malformed is an Error, which under (a) calls an Error what the reader reads as ISO says, and 'read in part' is untrue under (a) (every row is read); fits only (b)'s superseded case.
- Other new names, e.g. diagnostic xref.entry-null (naming what the reader did under (a)) or xref.entry-type-unknown: Same cost as the recommended option; names chosen by the maintainer.

Why: A reserved row is its own fault with its own reading; folding it into a malformation or a partial read would misstate it under (a) and force an Error ADR 45 does not support.

### Q221-4 (#221)
Which severities: the rule's under ADR 45, and the reader diagnostic's PdfDiagnosticSeverity?

- [R] Under (a): rule Warning, reader Warning: The file breaks 7.5.8.3 (types 0–2 only) and is read as 7.5.8.3 says — no rebuild, no loss, no choice — as object.reference-missing (null per 7.3.10) and xref.object-past-size (Table 15) are Warnings; the reader's Warning ('the result may not be what the caller expects') matches xref.section-missing and xref.entry-out-of-range.
- Under (a): rule Error: On the ground that what a later version's type stands for is lost to the reader; contradicts the precedent of object.reference-missing, and nothing is rebuilt or chosen.
- Under (b): two rules, Warning where no older row stands and Error where one does (or one rule at Error): ADR 45's one-rule-one-severity: the superseded case is the reader choosing what the file does not designate; telling the cases apart costs a set of skipped numbers bounded by the index guard, checked once the chain is read; one Error rule over-calls the case where ISO and the reader agree (null).
- Reader Repair instead of Warning: 'Not conforming and the reader worked around it' — defensible, though under (a) the reader follows the specification rather than working around it.

Why: Under the recommended reading the file is read exactly as the specification says, which ADR 45 calls a Warning; the reader's Warning matches the other diagnostics that leave an object null.
