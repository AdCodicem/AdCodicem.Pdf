## Questions

### Q1 (#264)
How far does 'a section a guard stops still judges what it names, without reading past the guard' reach: the three paths #264 names only, or also the /XRefStm of a guard-stopped table and the table's /Prev when its hybrid /XRefStm stream is what the guard stops?

- [R] P1: the three named paths, plus /XRefStm outside the file, plus the hybrid-stream stop (recommended): In a guarded read, an /XRefStm 99999999 is reported as read whole (Warning xref.section-missing + Error xref.section-not-found), and a hybrid table's /Prev outside the file, naming itself or naming its own stream is reported as read whole (xref.section-missing/xref.section-not-found or Warning xref.chain-cycle/Error xref.chain-loop). Same codes and severities as a whole read (ADR 45). About 30 more source lines than P0 (JudgeStreamPastGuard, the hybrid branch going through the same pastGuard judgment), 8 more tests (already written in proto-tests.diff), and docs can say 'a section a guard stops' without exception. Suite 9,324 / 0 failed; corpus unchanged.
- P0: /Prev on the three named paths only: Smaller diff (proto-p0-src.diff). The /XRefStm-outside and hybrid-stream rows stay as on main: a guarded read silent where the whole read reports an Error. Needs a new 'debt' issue under M02 for that gap, and the docs must name the exception. Suite 9,315 / 0 failed.

Why: The faults are of the same kind as #264's (an offset outside the file, a section already read), equally visible without reading past the guard. The hybrid case is the same kind of break (3080-3087) as the full-index break (3052) that #264 names. Leaving them makes the ADR 34 amendment and the reader-limits docs false for hybrid files, which batch 16 already took care to cover for the object guard.

## decided_without_question

- A fault found past the guard marks the index incomplete exactly as read whole, so the index is rebuilt on demand. The existing report paths do it by construction (SectionOffset 5207, the loop block 2954, ReportMissingSection 3210). Batch 16's FaultBesideCut path (4105-4120) set the precedent that a file fault seen beside a guard cut keeps the whole read's consequence. LoadObject (5546) already puts a damaged index's rebuild before a guard's null. Without it, objects only the older sections index would read as null and be presented as Unindexed, blaming the guard for the file's damage. Measured consequence: with /Root 1 0 R only in the older table, the guarded read now rebuilds at opening and serves the catalog, as the whole read does (main served null as RootHiddenByGuard).
- What might be sound stays the guard's: a reference to a number a row past the cut may hold (MayBeLeftUnread: any number for a table, the declared rows past the cut for a stream), and an offset in the file the chain has not read. Measured: the '30 0 R' and 'older table' shapes are unchanged by P1 (guard's report alone, TrailersHiddenByGuard true, no rebuild).
- An in-file /Prev offset is not probed for a section header. That would read the older section the guard ends the chain before (ADR 34: 'the chain ends at a cut ... since an older section, or its trailer, would stand for what the cut left out'), and the issue's frame is 'without reading past the guard'.
- References are judged through the existing SectionOffset/LeadsPastIndex, so a free row read before the cut, a regular row that is not an integer, a compressed entry, object 0 or a refused number reads exactly as in a whole read. AddFromChain keeps the first row, so hidden rows cannot redefine a number already held.
- The loop and outside-the-file judgments go through the chain's own code (the pastGuard flag continues to the offset). Records (LoopOffset, NotFound 'lies outside the file'), messages and positions are the whole read's, and the validator needs no change: SectionNotFoundRule and ChainLoopRule read those records, and TrailerValueWrongRule.IsFollowed drops the reference-form warning as in the whole read.
- A relocated cross-reference stream whose rows a guard cut has its /Prev judged: its dictionary is in hand and merged, and a whole read judges a relocated section's /Prev (relocated-p1.txt). A relocated classic table cut by its length does not, since its trailer is never looked for past the guard (3592-3595: 'each guess would read the file to its end').
- A /Prev in a trailer MaxTrailerLength cut (TrailerCutByLimit) is not judged. A value that touches the cut may itself be cut, and the parser does not say which values are whole. Listed as a neighbor.
- ThrowOnLimit is unchanged: every guarded shape throws PdfLimitExceededException at opening on main and on P1, because the guard is reached before the trailer is read.
- E1's tests stay in GuardCutValueTests, where batch 16 put them (A_cross_reference_stream_s_prev_a_guard_cut_ends_the_chain_as_the_guard_s and siblings, per #264's first comment). The issue's 'tests in ReaderLimitsTests and CrossReferenceRuleTests for E1, F and G' is met for F and G with 32 cases.
- Corpus: no change is possible (0 limit.* reports in 403 documents) and none was measured (byte-identical dumps).

## interactions

- relocation (#188, #281): the pastGuard loop test uses 'visited', which holds written offsets, as the loop block does. If #188 changes what 'already read' means (positions, sections found near where named), the pastGuard test at the top of the loop must follow. A /Prev naming the real position of a relocated guarded section is #188's false-loop shape; P1 treats it as an in-file offset (the guard's). P1's relocated-stream judgment relies on TryRelocateXRefSection accepting a rows-cut stream candidate as Read (3307-3322).
- partial (#207, #210, #222): the MaxXRefSectionLength path returns '_xref.Count > 0' (3610). If that decision changes (a cut before any row is indexed), the not-Read path (ReportLostSection, cut → break) drops _previousPastGuard and the judgment must move with it. Sections read in part by the file's fault (section.Incomplete) are not guard stops and are untouched.
- stream-prev (#208): if the chain learns to follow the /Prev of a stream whose rows cannot be read, P1's 'judge, never read' pastGuard mechanism is the tool for the guard-cut variants, which still return without judging /Prev: CutByValue, and FaultBesideCut with rows > 0 at 4113-4118.
- xrefstm (#156): JudgeStreamPastGuard passes silently over an /XRefStm the chain already read, mirroring the whole read. Whatever #156 decides to record for an /XRefStm naming a section already read must be applied in both places. P1 does not read an in-file /XRefStm under a guard (the guard's).
- messages (#241): P1 adds no message; its reports reuse ReportMissingSection and the loop text, so #241's shared plural/number helper covers them.
- window (#197, #261): no interaction. pastGuard never searches near an offset: in-file offsets break, and outside ones return at 3247 before any search.
- #292 (batch 27): with a rows guard plus MaxObjectLength, a /Prev object whose header is cut already rebuilds on main, through NamesOlderSection → LeadsPastIndex → ReadWithoutLoading. P1 leaves this byte-identical (objcut-main.txt = objcut-p1.txt), so #292's fix must cover the rows-guard path too.
- flaky (#317): the only failure seen in any suite run was that flake (ratio 8.9 against 8 under load); it passed when rerun alone and in later full runs.
