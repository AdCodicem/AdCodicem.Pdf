# Threat model

What the library defends against, how, where each defense lives in the code, and which test fails if it goes.
It is one document for the whole library ([ADR 46](adr/0046-every-milestone-ends-with-an-adversarial-review.md)).
A milestone that opens or widens a surface a hostile input reaches completes its section **in the same change**.
Every milestone's review checks the code against it (`docs/milestone-review.md`, *Security*). Read it before you
touch a parser, a decoder or a resource loader (`CLAUDE.md`).

This first version was written on 2026-09-30 and 2026-10-01 against `13e06bb` ([#135]). It covers what exists
there: the reader (M01) and the validator (M02, slices 1 to 3). Each defense below was checked against the code as
it stands, and each test it names was read. A defense found missing is not written as if it held. It is listed under the
*Known gaps* of its surface, with the issue that pays it.

## How to read it

- A **threat** is what a file can make the library do: exhaust memory, the stack or time, read out of bounds,
  throw something untyped, return a wrong answer, or reach the host.
- A **defense** is the code that stops it: a bound, a visited set, a check, an iterative walk.
- **Held by** names the test that fails if the defense goes. **Fuzzed** says whether the mutation campaign
  reaches the code at all (*What holds the defenses*, below).
- A bound is classified as [ADR 34](adr/0034-every-valid-pdf-is-readable-and-the-readers-guards-are.md) requires.
  A **guard** is a `PdfReaderLimits` property, on by default and reported under a `limit.*` code: a valid file
  may reach it. An **internal constant** is a bound that only an invalid file reaches, and the reason is written
  where the constant is declared. A bound on what the library repeats of a value, not on what it reads, is an
  internal constant too, though a valid file may reach it, and its declaration says so: a message quotes 127 bytes
  of a name ([ADR 34](adr/0034-every-valid-pdf-is-readable-and-the-readers-guards-are.md), amended 2026-10-01).

## Assets

What a caller entrusts to the library when it opens a file it did not produce:

- **The process's memory.** Memory follows the heaviest object the caller touches, not the size of the file
  (invariant 2). No allocation is sized by a value from the file without a checked bound (invariant 4). The eight
  guards cap what a valid but exceptional file may make the reader hold. Two of the validator's walks still hold, of a
  hostile file, more than the reader's cache ([#309], [#311]).
- **The process's time, and the calling thread.** The aim is that every call does work in proportion to the bytes
  it reads, under the guards. Some shapes break it today ([#181]). No call can be
  canceled yet ([M03] slice 9, [M23] slice 11). A .NET thread cannot be aborted, so a slow call holds its thread
  until it returns.
- **The stack.** A `StackOverflowException` cannot be caught in .NET: it ends the process. Every recursion whose
  depth a file chooses is bounded, and the reader, and the validator's walks of the object streams, also ask the runtime
  whether stack is left (`RuntimeHelpers.TryEnsureSufficientExecutionStack`) before they go one level deeper.
- **The caller's resources.**
  - `Open(string)` opens a read-only handle (`FileShare.Read`) and holds it until `Dispose`.
  - `Open(ReadOnlyMemory<byte>)` reads the caller's memory where it lies, without copying it.
  - `Open(Stream)` reads the caller's stream from its start when it can seek, from where it stands otherwise, and
    leaves it open. Only a `MemoryStream` itself is read in its buffer; a derived one, which may lend its buffer again
    once disposed, is copied.
  - `Open(PdfFileSource, …)` releases the source when it was given to own it, on failure too.
- **The truth of what the library returns.** A caller decides on the objects, the decoded data, the diagnostics
  and the validation report. Should an upload be accepted? Is the document encrypted? Did the reader cut
  something? A file that makes the report lie defeats the caller as surely as a crash does. That covers hiding its
  encryption, hiding a cut, or getting the reader's own limit blamed on the file.
- **The host's logs and terminals.** Diagnostic and finding messages quote names and keywords from the file, and
  hosts log and print them, as they print the objects a document hands out, through their `ToString`. A quote is
  printable ASCII on one line and at most 127 bytes of what the file wrote, and what an object says of itself is too,
  127 characters of a string's text at most, so what a host prints is the library's text, not the file's (*Reports*,
  below).

The library holds more later: the files it writes ([M03]), the original bytes and existing signatures an
incremental update preserves ([M03], [M04]), passwords and file keys ([M16]), signing keys and certificates
([M26]), access to the network ([M12]'s resource loader, [M26] and [M27]'s clients), native code in the process
([M12], [M25]), and caches shared across documents and renders ([M08], [M12]). *Surfaces still to come* lists
each with the milestone that brings it.

## Attackers

- **Whoever wrote the file's bytes.** That is the author of a PDF the caller opens: an upload, an e-mail
  attachment, a document received for a case file. They control every byte. They can iterate offline against the
  same package and the same public source. They want to crash, hang or exhaust the host. They want the library to
  return something other than what the file holds, or a report that hides what the file is. Later, they will want
  to reach the host: its files, its network, its secrets.
- **Not the caller.** The caller's code is trusted, and so are its options, the path it names, the stream or
  memory it passes, a `PdfFileSource` it writes, and the process's environment. A caller that raises a guard, or
  chooses `PdfReaderLimits.Unbounded`, accepts what the raised bound allows ([SECURITY.md](https://github.com/AdCodicem/AdCodicem.Pdf/blob/main/SECURITY.md)).
- **Whoever could alter the package** between this repository and nuget.org, or a dependency on the way in. See
  *The package and its supply chain*.

## Trust boundaries

Where a byte from outside the caller's code enters today:

| Boundary | Where | What crosses |
|---|---|---|
| The file source | `PdfDocument.Open(string)`, `Open(ReadOnlyMemory<byte>)`, `Open(Stream)`, `Open(PdfFileSource, PdfReaderOptions?, bool)` | Every byte of the file, read lazily through windows |
| What the reader derives | `GetObject`, `PdfReference.Resolve`, the `PdfObjectExtensions` accessors, `Trailer`, `Catalog`, `ObjectNumbers`, `PdfStream.GetRawBytes`, `Decode` | Values the file chose, handed to the caller's code. A later read that rebuilds the index changes what the next call gives, never what a call gave before it or gives after it; only a caller's own `PdfFileSource`, asking from inside the rebuilding read, can take a trailer the rebuild still changes ([#167]); a rebuild the source fails, in its scan or its finish, is run again by the next read or validation, and the calls between give the unfinished rebuild's index and trailer, and `Catalog` reads that trailer's `/Root`, which need not name a catalog |
| Messages | `PdfDiagnostic.Message` and `ToString`, `PdfValidationFinding.Message` and `ToString`; the `ToString` of the objects a document hands out — `PdfName`, `PdfDictionary`, `PdfStream`, `PdfString`, `PdfReal` | Text that quotes names and keywords from the file, escaped and cut; a string's text, escaped and cut; a real's shortest decimal |
| The validator | `PdfValidator.Validate` | The same document, plus bytes the validator reads itself: the file's tail, each entry's header read as a load reads it, object stream headers, and each member whose bytes hold `stream`, parsed as a load parses it |

Every surface still to come adds a boundary of its own: HTML, CSS and template data, the resource loader, font
programs, image files, content streams, XML, encryption, signatures and the network, DOCX packages and e-mail.
*Surfaces still to come* lists each one.

## Defenses every surface shares

### The guards

|---|---|---|---|

| `MaxStreamLength` | 256 MB | `limit.stream-length` | One stream's encoded data, read in one piece each time it is asked for, by `GetRawBytes` or a decoding (`FileStreamData.GetBytes`): past it the data is cut, and what lies within it is decoded as data the reader cut, whose lost tail is no damage. | `MaxObjectLength` | 16 MB | `limit.object` | The window a regular object is parsed through, grown ×8 from 8 KB (`PdfFileReader.TryParseNumberedAt`), and an object stream member's, from its start to the next member's (`ObjectStreamMemberWindow.Of`, `ReachMemberLimit`). A stream's data never counts toward it: no window is grown to find an `endstream` ([#174]) |
| `MaxXRefSectionLength` | 64 MB | `limit.xref-section-length` | The window a classic cross-reference table is read through, which opens where the table is read, the white space and comments an offset that names it falls short by included ([#289]) |

Reaching a guard keeps what fits and reports its code (`PdfLimitGuard.Reach`): once per position for an object written
in the file, a section, a trailer or a stream's data, once for each member of each definition of an object stream — at that stream's
data start, which its members share —, once per document for the index, and for a stream decoded past the bound once in its document's
diagnostics, each time into diagnostics the caller passes, counted each time either way ([#144]); data `MaxStreamLength`
cut, reported once at its position in the document's diagnostics, reaches diagnostics the caller passes with each decoding
that meets the cut too ([#170]). What a guard
leaves out of the index reads as null until it is raised, and the index is not rebuilt for it: a guard's cut is no
damage. A value read through a reference to an object a guard cut or left out of the index, through a chain of
references too, is the guard's as well, whatever the cut left of it — null, or a token it parted —, and the reader
judges none of it as the file's — but for a whole reference the cut left after the value, which is read through as a
load reads it, what it leads to judged as read whole. That holds for a stream's `/Length` ([#224]) and the values its filters read
([#263]), for a cross-reference stream's `/W`, `/Index`, `/Filter` or `/DecodeParms`, or `/Size` with no `/Index`,
that `MaxObjectLength` cut as the chain was read, and its `/Length` when no `endstream` ends its data, and for a `/Prev`
or `/XRefStm` the reader follows that leads to such an object (*Indexing*); it adds no bound. When the document was opened with
`ThrowOnLimit`, reaching a guard throws `PdfLimitExceededException` instead. A stream read from a document
decodes under that document's guards, however long after opening. `PdfReaderLimits` refuses a bound of zero or
less and takes a length past `Array.MaxLength` as that length. Held by `ReaderLimitsTests` throughout; the
mutation campaign opens with the defaults and never with `ThrowOnLimit`.

### Iteration, visited sets, and the stack

- **The parser recurses**, one frame per container level. Two things bound it: `PdfObjectParser.MaxDepth` (128)
  and a stack probe at each container. Past either, the container is skipped by counting brackets, with no
  recursion, and reported as `syntax.depth-exceeded`.
- **Loads nest.** An indirect `/Length`, an object stream's dictionary or a filter parameter loads another object
  while one is being parsed. `PdfFileReader.MaxNestedLoads` (64) and a stack probe before each load bound the
  chain; `_loading` turns a load that needs itself into null. A stream resolves its filters and every parameter they
  read before any of its data (`FilterChain`), so that no level of the chain holds decoded data while the next loads. While the cross-reference chain is read, nothing
  loads: what the chain refers to is read where a section already read places it, under the same bounds (see
  *Indexing*).
- **Every walk the validator makes across objects is iterative but one**, with a visited set by object number: the
  object graph, the page tree, the Arlington walk, and name and number trees. The walk of what decoding each object
  stream reads follows each chain of references in a loop, and recurses as the reader's loads nest: a stream met on a
  chain has its `/Length` followed one call deeper, at most `MaxNestedLoads` (64) levels, and the walk that works out
  whether an object stream decodes alike runs inside the one that met its object, one at a time, so that no recursion
  goes deeper than twice that bound. Standings that wait on one another are worked out on a stack of their own. A
  stream a later walk meets again is pushed again, and its entry lower down is left stale, its stream known by the time
  it is reached; the stack is rid of such entries, keeping the topmost entry of each stream not known yet, whenever it
  holds more than 1,024 and twice as many as it kept the last time. It so holds no more than twice the most streams
  waiting at once, or 1,024 entries, whichever is more, besides one walk's unknown streams
  (`HostileInputTests.Object_streams_whose_standings_wait_on_one_another_wait_on_a_stack_within_twice_their_number_and_one_walk_s_unknown_streams_whatever_the_walks_that_met_them`,
  `Object_streams_whose_standings_wait_level_after_level_are_rid_of_every_entry_of_a_known_stream_once_their_stack_holds_more_than_1024`,
  `Object_streams_whose_standings_wait_on_one_another_keep_every_entry_of_their_stack_until_it_holds_more_than_1024`,
  `A_walk_of_a_standing_that_meets_more_object_streams_not_known_yet_than_the_stack_keeps_before_it_is_compacted_leaves_them_all_waiting`).
  Kept, the entries of streams known already grew with every stream the stack ever held: 5,008 entries for 80 levels
  of 64 streams, of the 5,343 it held, where 144 waited at once ([#312]).
  On first run, both walks together take some 110 KB at the reader's nesting, about 0.8 KB a level. With the reader's
  own 64 loads under a value they read through it, about 5.8 KB each, the deepest validation goes some 480 KB deep,
  420 KB on the deepest shape measured. With the 128 KB the reader's stack probe keeps free above its deepest load, it
  needs a thread of some 610 KB for the probe to cut none of its loads — on that shape, none is cut from 560 KB.
  Recompiled by tiered PGO, as a process leaves them once it has run them a while, the walks take 0.8 to 1.0 KB a
  level, as the profile it gathered makes them, up to some 130 KB at their deepest, and a load about 8.3 KB: the
  deepest validation goes some 670 KB deep, 535 to 580 KB on that shape, and needs a thread of some 800 KB — on that
  shape, none is cut from 720 KB. A thread of 1 MB has room for either, with some 220 KB to spare once recompiled.
  The walks ask the thread for room themselves, before each level they go down, as the reader does before each load:
  what the reader serves from its cache, and what the walks keep, is read with no load and no probe, so that, of a
  document read before, the walks went their whole depth with none on the way — from a caller with less stack left
  than that depth, past its end, and the process with it ([#312]). On a thread with less room, a probe cuts. The
  reader's, or its parser's, cuts a load the walks make through the reader, and the walks keep what that read gave,
  for the rest of the validation, as it gave it ([#163]). The walks' own cuts a level they would go down, which reads
  as null — the walk of a standing then takes its stream, for the rest of the validation, for one that does not
  decode alike, and no parse the cut leaves short gives a nest a later walk would take —, and which the document
  reports once, under `syntax.depth-exceeded`. Either way, the report can depend on the thread
  (`ObjectRuleTests.The_deepest_walk_gives_the_same_report_on_a_stack_of_256_KB_as_on_a_thread_of_its_own`
  holds the deepest shape on 256 KB, where the probe cuts its loads, to its report on 1.5 MB, where it cuts none;
  `The_walks_of_a_document_the_reader_holds_whole_are_cut_rather_than_run_past_the_end_of_the_stack` validates that
  shape, held whole in the reader's cache, from a caller below the first frame the probe fails at;
  `A_value_the_walk_that_judges_has_no_room_on_the_stack_to_load_reads_as_null`,
  `A_stream_whose_standing_the_stack_leaves_no_room_to_work_out_does_not_decode_alike` and
  `A_walk_with_room_for_a_nest_follows_it_whole_wherever_the_stack_cut_an_earlier_walk_inside_it` hold what a cut reads
  and keeps).
  Its loops are found by Tarjan's algorithm on a stack of its own ([#277],
  [#168]). The two searches that place a fault inside one object once the object graph's walk is done — a reference to
  nothing, a name with a null character — read it in a loop over that walk's own array of containers, and a page tree
  kid's path is written in a loop, however deep a caller nested the value or the nodes above it ([#168]).
- **Chains are followed once.** The `/Prev` chain keeps the offsets it has read. `PdfReference.Resolve` fetches
  at most `MaxChainLength` (32) objects, so a chain of 31 references to references already reads as null ([#173]).
  The index is rebuilt at most once per document (`_repaired`).
- **Reports are made once.** A guard is reported once per `(limit, position)`, a full index once per document, what
  decoding a stream met — its filters' faults, a guard on its decoding — once per report its document's diagnostics
  hold ([#144]), a stream's length fault once per
  data start, a fault of the syntax once per report the diagnostics keep — its code, position and message —, and a
  search for a lost `endstream` runs once per data start.

### Tables keyed by numbers

A file chooses its object numbers, the offsets its rows and `/Prev` give, and where its streams lie. An `int` is its own
hash, a `long` its two halves exclusive-ored, and .NET puts a key in the bucket its hash leaves modulo a prime anyone can
read: numbers a multiple of that prime apart once put the index, the object cache and the validator's sets in one
bucket, every lookup walking tens of thousands of entries ([#155]).

- **The index finds a number in a slot while numbers run in order** (`PdfXRefTable`): an array no longer than twice
  the entries it holds or has made room for, and 1,024 more, then a map hashed through the process's seed. A file that
  spreads its numbers out fills the map, which gives back the room of the numbers the slots come to reach once most of
  it is idle.
- **Every other table keyed by numbers hashes them through that seed** (`SeededComparer`), the one .NET draws once a
  process for `System.HashCode`, as it draws another for strings, both halves of an offset mixed in apart: the reader's
  cache, its object streams, its sets and memos, the copies it marks and restores, and the validator's walks.
  `PdfObjectId` and `PdfDiagnostic` hash through it too, so that a caller's table keyed by them is spread alike.
- **No order the hashes give reaches an output.** A table enumerates in an order set by what was added to it and removed
  from it, never by its keys' hashes, so that a seed that differs from one process to the next changes nothing the
  library reports or writes (invariant 6). The library builds no table that enumerates by hash — concurrent, frozen,
  immutable, a `StringDictionary` or an obsolete `XmlSchemaCollection` —, whatever its key and comparer, which the
  reading of the compiled library below holds, but `PdfName`'s interning table, keyed by strings, which .NET hashes
  without a seed until a chain grows long, and through the strings' seed after, and which nothing enumerates. An
  unordered parallel query orders what it gives by partition and scheduling, whatever its comparer: the reading holds a
  parallel hashing operator's key and comparer as it holds `Enumerable`'s, but not that order, and the library runs no
  parallel query, parallelism never being implicit (`architecture.md`, *Parallelism*).
- **Two tests read the code** (`SeededComparerTests`). One reads the compiled library and refuses every hash collection
  built over a key a file can steer — a number wider than a byte, nullable or not, a tuple or an anonymous type holding
  one, a type of the library hashed as the compiler writes a record's hash or a record that is not sealed, which one so
  hashed may derive from, a type deriving from a tuple holding one, a pair or another struct that keeps .NET's default
  hash, or hides it with `new`, which a table does not call, and which hashes one holding a reference, a floating point
  number, padding or a field with an equality of its own by its first non-null field alone — unless the comparer of its
  key, taken last, is `SeededComparer.Instance`, handed to it straight on every path that reaches it: a constructor, a
  base constructor or a LINQ operator, or any of them as a method group. It refuses always a table keyed by any object,
  a boxed number hashing as itself — a `Hashtable`, a type derived from one, or its kin, a `DictionaryBase` among them,
  however built, or returned under its own type, a key typed `object`, `ValueType` or any interface, behind which a
  boxed number, tuple, record or struct may stand, a reference comparer given or not: an identity table is keyed by a
  reference type of the library —; a collection that enumerates by hash — a concurrent dictionary, a frozen or immutable
  one, its factories, its builder and an immutable one's `Empty`, a `StringDictionary` or an obsolete
  `XmlSchemaCollection`, however built — whatever its key and comparer, but `PdfName`'s interning table, which
  `PdfName`'s static constructor builds once, ahead of every branch target and straight into a static field, and which
  the library reaches, through its type or a generic interface of it, only to find or add one name — through `GetOrAdd`,
  `TryAdd`, `TryGetValue`, `ContainsKey` or the indexer's getter, let be whatever they are handed, a `GetOrAdd`
  factory's argument included, which reaches the factory only through `object` or a non-generic interface, which the
  reading does not follow, a factory typed over the table or a view of it being refused where it is built —: a call to,
  or a method group of, a member that takes it, gives it, views it or names its pairs, in an array, a reference or a
  type argument included, at any depth, or a static field declared on a type built over its pairs or a view of it, is
  refused, and through `object`, a non-generic interface or an expression tree, which names its members by token, it is
  not followed; and a table over such a key, a key holding a type parameter, or one that enumerates by hash, built for a
  type argument by a `new()` constraint, or for it or any type parameter, whatever its constraints, by the library's own
  `new()`, which compiles to `Activator`, or by `Activator`, `Lazy`, `LazyInitializer`, a `ConditionalWeakTable`'s
  `GetOrCreateValue`, a `BindingList`, which builds one for `AddNew`, or `Marshal.PtrToStructure` — the builders a sweep
  of .NET 10's shared framework found that may build a table, none handing it a comparer, a `Lazy` or a `BindingList`
  one of them builds counting as the table it builds in turn —; and a generic JSON deserializer of `System.Text.Json` or
  `System.Net.Http.Json`, whatever its type argument, which builds every table that type holds with .NET's default
  comparer unless its options or the type say otherwise, out of the reading's sight: the library reads no JSON. The
  library builds no type parameter it is given, generic code taking a factory instead: what its callers give it, through
  a dispatch, a constrained call or a default implementation as well as a call, is not all read. The library builds no
  hash collection over a key holding a type parameter, at any depth, whatever its comparer, since its callers choose the
  key; how the hash of a type the library hashes by hand spreads is held by its own tests, as `PdfObjectId`'s and
  `PdfDiagnostic`'s are; a collection built through reflection otherwise, an `UnsafeAccessor`'s among them, whose body
  the runtime writes, or one a framework method returns under another type, is not read. It reads through the probes
  code coverage puts, and only their shape: any other instruction between the comparer and the table refuses it. The
  other reads the sources and names the file and line of the shapes it recognizes.

### Everything read is bounded by the source

`PdfFileSource.GetWindow` returns an empty window for a range outside the source and clamps the rest.
`FileSource.Read` loops until the buffer is full or the file ends. A pooled window goes back to its pool at the
end of its `using`, and parsed values are copied out of it, so nothing a caller holds points into a rented buffer.
Held by `DocumentReaderTests.A_source_reads_nothing_outside_itself`,
`A_source_gives_an_empty_window_for_a_range_outside_itself_or_of_no_length`, and every test that reads through
`StrictCountingSource`, which throws on a read past its end or of no byte.

The reader's side of a source's contract is written on `PdfFileSource.Read`: it asks a source only for bytes the source
holds — an offset of at least 0, a buffer never empty, the two ending at `Length` at most —, however damaged the file,
so that a source a caller writes may refuse any other read, and the validator's reads keep to it as the reader's do
([#167]). Two reads asked for no byte: the search for `endstream` where white space after a stream's data ran to the end
of the file, and a stream of no length on a source not held in memory. Neither is made. What a count shorter than the
buffer means is [#52]'s. Held, beside every test above, by
`StreamLengthTests.White_space_from_a_stream_s_data_to_the_file_s_end_is_read_to_its_end_and_no_further`,
`Data_of_no_length_is_read_from_no_source`; and
`CrossReferenceRuleTests.An_entry_placing_its_object_at_any_of_the_file_s_last_bytes_is_checked_without_asking_the_source_past_its_end`,
`A_startxref_naming_any_of_the_file_s_last_bytes_is_followed_without_asking_the_source_past_its_end`,
`A_file_cut_short_anywhere_in_its_last_bytes_is_read_without_asking_the_source_past_its_end`,
`An_object_ending_the_file_inside_its_stream_is_read_without_a_read_past_the_end_or_an_empty_one` and
`A_cross_reference_stream_with_no_data_is_decoded_without_an_empty_read`, which open and validate each file over the
strict source and give the report and diagnostics the file gives in memory.

### Reports

`PdfDiagnostics` keeps `PdfReaderOptions.DiagnosticCapacity` entries (1,000) and counts the rest in
`SuppressedCount`. `PdfValidationReport` keeps `PdfValidatorOptions.FindingCapacity` findings (1,000) and counts
the rest by severity and rule. Both bound the **number** of entries, and the validator builds no more of them than its
report keeps: each analysis writes, of each kind of fault, the findings the report has room for, and counts the rest
([#168]; *The validator*, below). A report's count past what an `int` holds stays at `int.MaxValue`, the count of
findings not kept included, which the validation keeps apart rather than work it out from the counts by severity.
Billions of faulty values reach it, which a file of tens of kilobytes whose object streams decode to gigabytes can
give: two page tree nodes of 8,000,000 kids each, in one object stream deflated twice, are a file of 774 bytes that
counts 16 million findings.

An entry's **size** is bounded by how it quotes the file ([#159]). Every name and keyword a message quotes goes
through `FileQuote`, which writes it as a PDF writer writes a name: printable ASCII on one line, every other byte, the
number sign and the delimiters as `#xx`. Past `FileQuote.MaxBytes` (127) it is cut, with the whole's length, from a
buffer on the stack, so a name of 64 MB costs its quote and no copy. A path of keys in a finding keeps its first and
last `RuleText.PathEnds` (4) steps. A string from the file is never quoted. Numbers are written in the invariant
culture; a count agrees with its noun, and a distance is written as a size and the way it runs, never as a negative
number (`CountText`, [#241]), though some counts group their digits and others do not ([#326]). What the reader keeps of a stream's length fault for the document's life is the value it found, not words
about it. Held by `FileQuoteTests`; `CountTextTests`; `PropertyTests.A_quote_of_the_file_is_printable_ascii_on_one_line_and_bounded_whatever_the_bytes`;
`HostileInputTests.Reads_streams_whose_length_names_a_name_of_millions_of_characters_within_an_allocation_budget`,
`Reads_fifty_streams_whose_length_names_one_long_name_within_an_allocation_budget`,
`Quotes_a_keyword_of_ten_megabytes_where_a_subsection_should_start_by_its_first_bytes`,
`Validating_an_object_whose_key_path_holds_megabyte_keys_stays_within_an_allocation_budget`; and
`CorpusReadingTests.Every_message_a_document_earns_is_printable_ascii_on_one_line_whatever_the_culture`, under a Persian
culture.

What an object says of itself through `ToString` — what a debugger, an interpolation in a log line or a test runner's
failure message shows — follows the same rules ([#212]): a name is quoted through `FileQuote`, and so is the type a
dictionary or a stream gives itself by; a string's text is written between double quotes, every character outside
printable ASCII escaped as C# writes it in a literal, cut past 127 characters with the whole's length, decoding no more
of the text than it shows; a real is the shortest decimal that reads back to it, at most 327 characters. None copies
what it cuts. `Value`, `Bytes`, `ToText` and `GetRawBytes` stay the raw accessors. Held by
`ObjectModelTests.A_name_of_megabytes_and_what_it_types_describe_themselves_in_a_few_hundred_characters`,

### What may be thrown

From a file, only a `PdfException`: `PdfFormatException` for an input that is empty or holds no object,
`PdfEncryptedException`, and `PdfLimitExceededException` when the caller asked for it. Everything else that
escapes is the caller's: an argument it passed, the I/O of its own file or stream, a document it disposed. Any
other exception a file can cause is a defect, and the ones found are in the gaps below.

### What the library never does with a file's content

It opens no path, URL or process that a file names. It loads no type and writes no log. The only host access in
the core is `File.OpenHandle` on the path the caller gives, read-only. A search of `src/` finds no `HttpClient`,
`Process`, `Assembly.Load`, `Type.GetType`, `Activator`, P/Invoke, `Console`, `Trace` or logger.

The only shared mutable state the library keeps is `PdfName`'s interned table. It is a `ConcurrentDictionary`, so
it is safe to share across threads, but it grows for the life of the process ([#37]). Every other static value is an
immutable record or singleton. Windows and Flate buffers are rented from the process-wide `ArrayPool<byte>.Shared`
and go back to it uncleared ([#180]). A `PdfDocument` is not thread-safe, and nothing detects two threads using one.

## The reader

Everything below reads bytes the file chose. The reader opens a file by indexing it. It reads the header, the tail
and the cross-reference chain, or it rebuilds the index by scanning the file when the chain fails. After that it
parses only the objects a caller asks for, each through a window of the file, and decodes a stream only when the
caller asks for its data.

Known gaps:

- [#154] Encryption is decided by the merged trailer's `/Encrypt` key, unresolved. A rebuilt index loses one kept in a
  cross-reference stream and hands out ciphertext; one that resolves to null refuses an unencrypted file.
- [#180] Pooled buffers go back to the shared pool uncleared, and the windows a hostile file grew stay pooled, per
  thread, after the document is disposed.
- [#149] `Open(Stream)` copies a seekable stream into memory, as its documentation now says, where reading it in place would
  keep invariant 2.
- [#52] A source whose `Read` returns fewer bytes than asked is taken as the end of the data — not everywhere alike: the
  search for a lost `endstream`, after a read of no more bytes than the ten its reads repeat, may miss a keyword, a
  header, or the end of line before a keyword that no window then holds whole, an `endstream` in a comment among them,
  the data ending later; a short read of more ends the data where whole reads end it. Each read counts all it returns
  toward what the searches may read together (`EndStreamSearchPasses`), and the next starts one byte past where it
  started at reads of eleven bytes or fewer, ten bytes before where it ended at longer ones: about n times what whole
  reads count at reads of n bytes up to ten, eleven times at eleven, twice at twenty. So, however long the reads, the
  reads on past a keyword may stop short, its object's `endobj` then unjudged, and a later stream's data, running past
  the bytes read with its object, be taken up to the next object without a search. An `endstream` in a comment, once a
  read has held it whole and it waits, is decided as whole reads decide it, however short the reads after it.
- [#331] The search for a classic table's trailer past the rows a guard left unread reads one window again, without
  end, where a window comes back 32 bytes or fewer before the file's end, or empty: the library's own `FileSource`
  gives one for a file that shrinks while it is open, and so does a caller's source whose `Length` is larger than the
  data it serves. That search's test of whether a token starts at a window's first byte (`StartsToken(long)`) reads the
  byte before through a window of its own and takes that window's first byte, though it may come back empty. Making
  reads loop ([#52]) does not close it: a window still comes back short wherever the data ends before `Length`.
- [#191] A reference resolves through the reader, not the document: the reader refuses once the document is disposed,
  but which source a reference carries, and what M03's change set will show through it, is still to settle.

  reads what such a cut kept: a stream first decoded at the reader's deepest load, its nesting or its stack probe
  cutting a value its decoding reads, gives the value that cut left, whatever the walk would find, as long as the reader
  keeps it (`ObjectRuleTests.A_stream_the_reader_first_decodes_at_its_deepest_load_is_read_as_it_kept_that_decoding`).

  what the cut left, and reading the document first can spare it, or the reverse. The reader also asks its cache before

  `/Length` chain such a link carries past the cut can go on into a stream the reader still holds, which then reads as
  null for the rest of the decoding, with no load cut in either order

  the cut, not of the token it parted.

### Decoding

Flate data is inflated by native code: the runtime's `System.IO.Compression.Native`. Microsoft's builds link
zlib-ng into it, and distribution builds of .NET link the system's zlib. So a host that keeps its .NET runtime and
its zlib patched is keeping part of the reader patched.

## The validator

`PdfValidator.Validate` reads a document the caller opened, under that document's `PdfReaderOptions`. Whatever
it resolves goes through the reader and its guards, and joins the reader's cache. It adds reads of its own: before its
first rule, the header each entry written directly in the file places, and a rebuild of the whole index when a read
could still set one off (`PdfFileReader.SettleIndex`); the file's last 1,024 bytes (`EndOfFileMarkerRule`), the header of
every entry, read where it places its object as a load reads it (`CrossReferenceProbe`, through `PdfFileReader.PlaceHeader`), each object stream's header, decoded again outside the reader's budget
(`PdfFileReader.ReadObjectStreamHeader`), and each object stream's dictionary, with the objects written directly in the
file its decoding keys lead through, parsed where the chain's index places them, outside the reader's cache
(`PdfFileReader.ReadWhereChainPlaces`); a member of another object stream those keys lead through, when that stream
decodes alike in every read order, is read through the reader, which decodes that stream as any read does. It decodes
no content or image stream.

The rules share five analyses, each built once per validation (`ValidationContext`): the cross-reference
probe, the page tree walk, the object graph, the Arlington walk and the dependencies between object streams.
Guarding the validator means guarding them.

The validator has no guard of its own. `FindingCapacity` is an option on the report, visible through
`SuppressedCount`, and not a `limit.*`. What it costs follows the index, which `MaxIndexEntries` bounds: about 3 µs
and 350 bytes allocated an entry, measured on sound files of one and two million objects (3.0 to 3.4 s and 353 MB,
5.7 to 6.1 s and 705 MB), so that a file near the default bound, 8,388,607 objects, takes about 24 s and 3 GB to
validate. An entry costs no more on a hostile file: once the probe has consumed twice the file's length reading
headers, an entry its first 64 bytes do not decide reads those, and is said not checked — 20,000 entries that all lead
into one comment of 8,000 bytes read 178 bytes an entry in all, where they read 9 KB each before ([#175]) —; one they
decide is still searched for nearby, about 1 KB, and judged. A faulty entry costs no finding past the report's room,
only a count ([#168]). The bound is not a large file's alone: an 845-byte cross-reference stream of one-byte rows,
deflated twice, fills it, and settling holds twice the index, 640 MiB, the chain's beside the rebuilt one (*Indexing*);
validating its eight million broken entries then allocates 34 MB ([#181]). An application that validates
uploads lowers the guard to what it accepts.

Known gaps:

- [#309] The Arlington walk's queue holds the values written inside each object it has still to check until their turn
  comes, past the reader's cache: a flat tree of 2,000 pages, each with resources of 5,000 integers written in it, held
  354 MiB under a cache of 64 objects, and 12 MiB with the resources as objects of their own. What it holds follows the
  file, not `ObjectCacheCapacity`.
- [#311] The page tree walk holds the `/Kids` array of every node on its path: a deep path of nodes that each list many
  kids holds them all, some 40 bytes a kid, and a kid written in an array rather than referred to keeps its array until
  its node is left, visited or not — 89 MiB for a path of 500 such nodes. In a valid tree, what the path holds is of
  the order of what the walk keeps for its pages anyway, about 60 bytes a page: a page index and a visited mark, 36 to
  72 bytes in tables between half full and full.
- [#314] A loop between object streams that closes only through the value of an object whose stream does not decode
  alike where it is met goes unseen, with what decoding reads after that value — a stream that lies on a loop itself,
  which is reported circular in its own right; one whose decoding meets a stream again while the reader holds it in its
  loads, itself included while its `/Length` is resolved, though nothing it decodes reads it again; one the reader's
  nesting cuts where it is met; one a rebuilt index places otherwise. The reader reports such a loop as
  `stream.self-reference` as it decodes. The walk that judges parses each stream once a walk, as a reader that keeps it
  does: it neither reads as null, as the reader does for the rest of the judged stream's decoding, a stream that
  decoding met again while it held it, nor parses again a stream the reader's cache let go — deterministic, and able to
  name a loop the reader meets in no read order, or to miss one.
- [#313] The probe reads what an object stream's decoding reads — its `/Type`, `/N`, `/First`, `/Filter` and
  `/DecodeParms` — as the reader serves it. Where such a value is held by a stream that lies on a loop, or the stream
  lies on a loop itself, what the reader serves depends on which stream of the loop it decoded first. So do the
  verdicts of `xref.object-stream-broken`, `xref.entry-broken` and `xref.entry-shifted`: a stream taking its `/Type`
  or its `/Filter` from such an object is found broken after some reads and not after others, and so are its members'
  entries. A stream on a loop is reported circular rather than broken, but its members' entries still change with the
  read order.
- [#181] The dependency walk follows again, on each walk, a nest of streams by `/Length` that ends at an object of an
  object stream, loops back on itself, or meets a stream another nest parsed — nests sharing their last stream —, as
  the reader's decoding of each stream reads it again past its cache. It pays this once for each object stream, and
  once more for each holder a waiting stream's walk is made again for ([#315]). So it does every nest when more nest
  heads than `ObjectCacheCapacity` are met in turn: 33 or more sets of 256 heads sharing their tails (1.9 MB) cost each
  stream about 35 to 50 ms and 14 MB. What a walk pays follows what its parse of those nests loads: up to 5 heads a
  step, LZW's `/EarlyChange` included, for each of `MaxFilterChainLength` steps; each head a nest of up to 62 streams;
  each `/Length` through up to 30 more objects, read again past the cache. One shape, 256 heads each heading a nest of
  62 streams whose `/Length` names the next stream directly, costs 47 ms and 15 MB a walk. Under the default limits the
  walk measured up to about 67 MB and 0.5 s a stream for Flate, and 84 MB and 0.65 s for LZW, in files of 18 to 23 MB,
  where the reader's own decoding pays 20 to 25 MB a stream.
  `HostileInputTests.Nests_the_walk_cannot_keep_cost_each_object_stream_alike_whatever_their_number` pins the heads
  past the cache and the nests sharing their last stream at the smallest cache, by the least each stream costs there:
  about 64 KB for 20 sets of 4 heads met in turn and sharing 4 tails, and 141 KB for 8 parameters each heading a nest
  of 20 whose last `/Length` names one stream. A cache brings the heads past the cache to about 1 KB once their 80
  heads fit. The nests sharing their last stream have 8 heads, which fit already: they allocate about 1 KB only once
  the reader's cache holds every stream of their nests, and the walk still parses the other 140 streams again, which
  closing #181 removes. Closing #181 flips the pin.
- [#315] Each time a waiting object stream is taken up again, its walk is made again whole: once for each holder that
  hid from it, nests the walk cannot keep included. The walks of a validation stay within about three for each object
  stream, so that the total stays linear, but one stream can carry what many streams paid before. One stream hiding
  90 holders behind 10 levels of 10 links, its nests not kept, in 1.07 MB, costs 1.35 to 1.36 GB and 4 to 7 s, against
  36 to 55 MB and 0.3 to 0.8 s for the walk that followed only the objects of streams needing none. 16 streams that
  each hide 32 levels of 32 links, their nests kept, take 4.4 s and 191 MB, against 0.43 to 1.1 s and 89 MB. Keeping
  each value's outcome across one stream's walks closes it: a walk made again then follows only the values that read
  an object of a stream not known yet as null. The `waits` shape of `ObjectStreamDependencyBenchmarks` is to show the
  gain, or a `hidden` shape of a stream waiting on chains of holders joins it.
- [#169] Once the diagnostics are full, a guard reached is neither reported nor seen, and the validator blames the
  file for the reader's cut.
- [#173] The Arlington walk takes a reference to a reference for a missing key.
- [#218] A chain read whole that gives no row is rebuilt as the document opens, and no rule reports it.
- [#132] A document with no catalog at all earns no finding when its index was rebuilt at opening.
- [#229] A catalog whose own load rebuilds the index is tested by neither search for it: the trailer keeps a `/Root`
  that is no catalog, and `file.root-invalid` says no object is one.
- [#260] `file.root-invalid` says no object of the file is a catalog when one may lie past a guard, or when a rebuild
  made `/Root` one.
- [#276] An object a rebuild serves from another object stream than the chain's index places it in, or from another
  definition of that stream, which does not list it or holds it written as a stream, reads as null with no finding that
  names it: the probe judges the stream and the definition the chain's index places.
- [#325] `xref.section-malformed` judges a section only where its trailer has no fault: a section the reader could not
  read for a fault of its own — a `/W` with a negative width, a row that is no row — whose trailer is at fault too earns
  the trailer's finding alone, and no finding names the fault the reader reported.
- [#321] A hybrid table that names through `/XRefStm` an older revision's cross-reference stream two or more revisions
  late has that stream read before the revisions between, its rows standing over what they wrote, and no finding says
  so: each naming is recorded ([#156]), and no rule judges where the namings lie yet.

## What holds the defenses

- **Hand-written hostile tests**, on every commit: `HostileInputTests`, `HostileInputMemoryTests` (the memory left
  live, sampled as the file is read), `ReaderLimitsTests`, `ReaderTimingTests` (a ratio, not a wall-clock budget),
  `WindowEdgeTests`, `StreamLengthTests`, `GuardCutValueTests`, `FilterTests`,
  `FilterDamageTests`, `DiagnosticsTests`, and the validation rule tests. They hold the bounds a mutation of a small
  file cannot reach.
- **A reading of the code** (`SeededComparerTests`), compiled and as written: every hash collection built over numbers
  takes the seeded comparer, so that no table a later change adds hashes numbers a file chose as themselves; none is
  built over a key holding a type parameter, which its callers choose; and none that enumerates by hash is built,
  whatever its key, but `PdfName`'s interning table.
- **Budgets on real documents, and on a generated index.** `CorpusReadingTests` holds what indexing a 1,000-page document and walking its
  page tree allocate, and each operation on every corpus document — opening it, reading every object, walking its
  pages, validating a damaged one — to 20 s. `CorpusValidationTests.Validating_the_largest_document_stays_within_its_budget`
  holds validation to 6 MB. `DocumentReaderTests.Opening_an_index_of_three_hundred_thousand_objects_stays_within_its_memory_budget`
  holds opening a valid index of 300,000 objects to 5 % over its figure, through a classic table and a cross-reference
  stream ([#193]), and `Opening_a_chain_of_a_thousand_sections_resizes_the_index_no_more_often_than_doubling_it`
  through a chain of a thousand sections ([#164]). Every job that runs the tests on a change, and the documentation's deployment, stops after fifteen
  minutes. Throughput is not held in CI yet ([#38]).
- **The mutation campaign** (`FuzzingTests`, `FuzzingSeeds`, `.github/workflows/fuzz.yml`). It has three
  targets:
  - open a mutated document, resolve every indexed object and decode every stream without an image filter;
  - validate every mutant the reader opens, with no exception allowed at all;
  - parse the mutated bytes as one object, which in most seeds is only the first object's number ([#158]).

  The mutations are bit flips, digit rewrites, truncation, a random overwrite of 1 to 64 bytes, and a broken
  `endstream` or `obj`. Each input must finish within 5 seconds, checked once it returns, and allocate under 64 MB.
  The seeds are corpus documents of 120 KB at most, not encrypted, read under the default limits. Every commit
  runs 104 seeds 60 times each. Each night runs the smallest seed of each of the 32 reader structures plus 16 in
  rotation, 20,000 times each, so every seed is reached within five runs.
- **Properties** (`PropertyTests`, FsCheck): the lexer, the parser, the number parsers, text strings, window edges,
  the limits' validation and the end-of-file rule. 200 cases per commit with a fixed seed; 50,000 a night with a
  seed from the run number.
- **Referees**: qpdf, in a container, judges the corpus as we do (`QpdfRefereeTests`, `FlateRefereeTests`,
  `StreamLengthRefereeTests`, `ValidationRefereeTests`).

What none of them reaches is the subject of the gaps below. A mutation never makes a file longer, so nothing
size-dependent is fuzzed: the guards, the budgets, the rebuild's pieces. FsCheck's default sizes keep generated
buffers near 100 bytes and integers within ±100. No coverage-guided fuzzer exists yet ([M23] slice 11).

Known gaps:

- [#158] The parser target, three properties and three hostile-input tests hold less than their names claim, and
  several defenses have no test.
- [#176] The campaign never reaches RunLength, ASCIIHex, most predictor rows, any guard, encrypted files or inputs
  past 120 KB, and cannot see a read past the end.
- [#38] Throughput is not held in CI.
- [#194] The nightly campaign starts its seeds at 0 every night, so it runs the same mutants of a document each time.

## The package and its supply chain

- **The core has no dependency** (invariant 1): its project references no package and no other project. `ci.yml`
  fails a pull request whose packed core declares a dependency in its nuspec; a native one, through `[DllImport]`,
  is kept out by review alone ([#179]). The AOT and trimming analyzers run, and warnings fail the build. Unsafe code is off.
- **Workflows** declare read-only permissions at their top — `contents: read`, with `pull-requests: read` added
  in `commits.yml`, and `read-all` in `scorecards.yml`, whose one job replaces it with the four permissions it
  needs — and raise a permission per job where one is needed. Every action is pinned to a commit SHA. CI and the commit
  checks run on `pull_request`, so a fork's pull request gets no secret and no write token. The one
  `pull_request_target` workflow, Dependabot's auto-merge, checks out no code, and queues only an update
  `fetch-metadata` classifies as a patch or a minor. Every Dependabot entry waits a week before proposing a version.
- **Publishing** uses trusted publishing ([ADR 25](adr/0025-trusted-publishing-rather-than-an-api-key.md)): a
  key valid one hour, exchanged for the job's OIDC token just before the push, and no NuGet secret stored. The
  `AdCodicem.*` prefix is reserved on nuget.org. Builds are deterministic and carry their sources' location and
  symbols.
- **A preview is built where nothing can publish** ([ADR 49](adr/0049-previews-weekly-when-a-package-input-changed.md)).
  `preview.yml` tests in one job and packs in another, neither holding a credential; the pack restores only the
  packable projects under `src/` (one package, against 71 for the solution). The publish job, the only one in the
  `nuget` environment, runs no project code: it checks the artifact against the digests the pack job output, checks
  the set and that the plan is still current, attests every package and assembly, and pushes. The release tooling's
  npm packages run in a job of their own, whose only outputs are a version and a release type, which the plan
  computes again. Previews are attested; an assembly restored from nuget.org verifies with `gh attestation verify`.
- **A stable release is built where nothing can publish, and approved before anything does.** `release.yml`
  tests and packs in jobs with no credential, the documentation snapshot included. Its release job, in the
  `nuget-stable` environment, waits for the reviewer, builds nothing, checks the pack job's files against their
  digests, and runs semantic-release from the committed lock, without install scripts, beside the NuGet key and
  the release App's token; its own `GITHUB_TOKEN` only reads. The packages and their assemblies are attested, and
  the bundle is attached to the GitHub Release before it is published.
- **Test data is pinned**: remote corpus documents by size and SHA-256, the Arlington model by a lock file that a
  test checks.
- **Measured, not asserted**: OpenSSF Scorecard runs weekly and on every push to `main`. CodeQL runs as GitHub's
  default setup, which the ruleset on `main` requires.

Known gaps:

- [#177] The benchmarks' `filter` input still reaches `run:` by template expansion, and the qpdf referee's image
  and the commitlint action's image are pinned by tag, not by digest.
- [#178] A branch can publish a package without review: nothing ties the `nuget` environment to `main`.
- [#179] Only the packed nuspec is checked for a dependency of the core: not the assembly's references, a
  `FrameworkReference` or a `[DllImport]`.
- [#43] The NuGet restore is not locked.
- [#41] The release App on the ruleset's bypass list, and the CI checks required by name, are settings the
  maintainer has yet to make; until then the stable release stops at its first step.
- [#44] The project has no OpenSSF Best Practices badge.
- [#196] Dependabot's auto-merge queues only patches and minors, but nothing requires CI before the merge it queues
  until the checks are required by name (#41).
- [#195] The corpus build's Python producers are pinned by version, without hashes, and the packages they pull in are
  not pinned.

| ICC profiles | [M15], [M29] | ADR 34, 42 | Bounded header and tag-table readers, CLUT sizes computed in 64 bits before allocation, and fuzzing over fourteen nights. |
| Encryption and passwords | [M16] | ADR 41 | `/O`, `/U`, `/OE`, `/UE`, `/Perms` and `/Length` are checked before use, and decryption runs block by block through pooled buffers. Open: whether passwords and file keys are cleared from memory and kept out of exceptions and diagnostics. The managed MD5, RC4 and AES are not constant-time. |
| Forms, scripts and XFA; FDF and XFDF | [M16] | ADR 34, 37 | Scripts are recognized by pattern and never run. XFA and XFDF are parsed with `XmlReader`, DTDs prohibited. Field trees are walked iteratively. |
| E-mail: EML and MSG | [M18] | ADR 34, 38 | `EmailLimits` guards. CFB chains cut at the sector count, LZFu sizes checked before allocation, every remote reference refused. |
| Redaction and sanitization | [M19] | ADR 22, 37 | Always a full rewrite. A stream cut at a guard fails verification rather than passing it. |
| Conformance profiles over hostile documents | [M20], [M28] | ADR 36, 45 | Bounded header readers; the engine proved total by FsCheck. |
| Received documents converted to PDF/A | [M21] | ADR 22, 41 | `MaxAttachmentDepth` (3), with the attached streams' hashes. |
| Image codecs: CCITT, JBIG2, JPEG, JPEG 2000; color spaces and functions | [M22] | ADR 34, 35, 42 | `MaxImageWorkingSet`, `MaxJpegScans`, JBIG2 counts in 64 bits, a bounded PostScript stack, every decoder fuzzed. Open: the cost of a type 4 function evaluated per sample, and the size of the lookup table for an n-input `DeviceN`. |
| OCR text layers: hOCR, ALTO, TSV | [M22] | ADR 42 | `XmlReader` with DTDs prohibited; `MaxInputLength` 64 MB, typed, since it is the caller's input. |
| Optimization, the piecewise decode, hardening | [M23] | ADR 34, 35 | Cancellation within 100 ms on hostile input, the cache weighed in bytes, coverage-guided fuzzing, the container profile. |
| Comparison and templates | [M24] | ADR 15 | Bounded edits per window, `NonBacktracking`. |
| Rasterization | [M25] | ADR 16, 42, 43 | `MaxRasterPixels`, band and layer bytes, bounded mesh subdivision. No font program or codec reaches Skia. |
| Signing: TSA and remote-signing responses, deferred requests | [M26] | ADR 18, 41 | Network off by default, responses read up to a bound, the prepared file checked again before the second step. |
| Signature validation: CMS, X.509, OCSP, CRL, trusted lists, and the URLs they name | [M27] | ADR 41 | OCSP and CRL parsed by our own `AsnReader` code under explicit bounds, fuzzed from the day they are written. Path building uses a visited set. Open: no address, scheme or redirect policy is stated for the URLs a signed file names (caIssuers, OCSP, CRL). ADR 38's rules cover only the HTML engine. |
| DOCX packages | [M31] | ADR 37, 38 | ZIP limits checked before reading, part names validated, DTDs refused in every part, external relationships refused by default. |
| JSON inputs: plans, models, policies, templates, requests | [M06] onward | ADR 8 | `Utf8JsonReader` and source generation, no reflection. Open: several specifications state no depth or size bound. |

## Out of scope

- **Active content** ([ADR 37](adr/0037-out-of-scope-active-content-and-pdf-to-office.md)). JavaScript is never
  executed, dynamic XFA never rendered, 3D and rich media never authored. A file that carries them is read,
  validated and manipulated like any other, and what cannot be kept is reported.
- **The caller's own code and choices.** A `PdfFileSource`, a resolver, a codec, an OCR engine, a key source or an
  `HttpClient` the caller supplies is trusted. A caller that raises a guard, or chooses `Unbounded`, lets a file
  use what those bounds allow. That is by design, not a vulnerability.
- **A file changed under an open document.** `Open(string)` shares the file for reading, which Unix treats as
  advisory, and `Open(ReadOnlyMemory<byte>)` reads the caller's memory in place. Bytes that change after opening
  are read as they are then. A caller who cannot keep them still copies them first.
- **Concurrent use of one `PdfDocument`.** It is not thread-safe, as its documentation says, and nothing detects
  two threads using it.
- **Hard limits on a process.** The library does not sandbox itself. Until [M23]'s container profile, a host
  that must bound time or memory absolutely runs the library in a process or container it can stop.
- **What a page shows as opposed to what the file says.** The reader returns what the file holds. Whether a
  page's appearance misleads (an overlay, a field over signed text, white text) is for the milestones that
  render, compare or judge signatures to report.
- **Timing side channels.** None exists today. [M16] records that its managed MD5, RC4 and AES are not
  constant-time.

## Keeping this document

- A change that opens or widens a surface completes its section in the same pull request (`CLAUDE.md`). A new
  bound is classified when it is added (ADR 34). A defense that is missing is filed as a `debt` issue and named
  under *Known gaps*, never written as if it held.
- A defense named here is one that was read in the code. A test named here is one that was read.
- A milestone's review checks the code against this document (`docs/milestone-review.md`, axis 5). Any
  difference it finds is a finding.
