# M31 — DOCX to HTML

> State: to do — Depends on: M12 — The HTML engine renders what this converts, per [ADR 4](../adr/0004-business-documents-with-a-modern-css-subset.md); resources referenced by a document loaded deny-by-default, per [ADR 38](../adr/0038-the-html-engine-loads-resources-deny-by-default.md); a satellite with its own dependency, per [ADR 9](../adr/0009-a-dependency-free-core-plus-satellites.md); PDF to Office stays out, per [ADR 37](../adr/0037-out-of-scope-active-content-and-pdf-to-office.md)

## Goal

Put a Word document into a case file without an office suite: convert DOCX to HTML and CSS that the HTML engine
renders, with a fidelity that is approximate, measured and documented rather than hidden, and a diagnostic for
everything the conversion could not map.

A case file receives contracts, letters and pleadings as Word documents. Today the only route is LibreOffice or
Word upstream. This satellite gives a managed route for the business documents Word produces most — styled text,
numbered clauses, tables, images, headers and footers — and says plainly what it cannot do.

## Scope

**In**: the `AdCodicem.Pdf.Docx` satellite on the Open XML SDK (MIT): styles and their inheritance (document
defaults, paragraph, character, table and numbering styles, theme fonts and colours); direct formatting; numbering
(abstract numbering and levels, restarts, overrides) mapped to CSS counters and `@counter-style`; tables (grid,
merged cells, borders, shading, header rows repeated across pages); inline and anchored images, anchored ones as
floats; sections (page size, margins, orientation, columns) mapped to named pages; headers and footers, first-page
and even-page variants, as running elements; fields — page number, page count, date as a supplied value, table of
contents — mapped to counters and M12.6's table of contents, other fields as their cached result; footnotes and
endnotes on M12.7; hyperlinks and bookmarks; tracked changes shown as accepted by default, with an option;
comments dropped or kept as annotations, by option; embedded fonts deobfuscated into the registry for the
document; the alternate content Word writes for charts and SmartArt, used as its fallback image.

**Out, explicitly**: XLSX, PPTX and ODT (an open question of the roadmap); macros and ActiveX (never run, ADR 37);
editing or writing DOCX; exact Word fidelity — line breaks, page breaks and kerning will differ, and the
documentation says so.

## Design

```
DocxConverter              DOCX package → an HTML document with its stylesheet and its resources
DocxConverterOptions       immutable: tracked changes (final, original), comments (drop, annotate), the
                           resource policy for external relationships, the fallback fonts
DocxConversionReport       what was mapped, approximated or dropped, element by element
```

- **HTML is the interface.** The converter produces HTML and CSS, and the HTML engine does the layout; nothing in
  this satellite knows about PDF. A caller can inspect or adjust the HTML before rendering.
- **The package is hostile input.** A DOCX is a ZIP of XML: entry counts, decompressed sizes and nesting are
  bounded (invariant 4); XML is read with DTD processing prohibited; relationships that point outside the package
  (`TargetMode="External"`) go through the ADR 38 resolver and are refused by default.
- **Every approximation is a diagnostic.** A floating object placed approximately, a field shown as its cached
  result, a style property with no CSS equivalent: each is reported with the element it came from.

## Slices

1. **Package reading, bounded**: the ZIP and its parts through the Open XML SDK, with size, count and nesting
   limits and DTDs prohibited; external relationships refused and reported.
2. **Text and styles**: runs, paragraphs, the style hierarchy, theme fonts and colours, direct formatting.
3. **Numbering**: lists and numbered clauses as CSS counters and counter styles, with restarts and overrides.
4. **Tables**: grid, merged cells, borders, shading, repeated header rows.
5. **Sections, headers and footers**: page sizes, margins, orientation and columns as named pages; header and
   footer variants as running elements; page fields as counters.
6. **Images and anchored objects**: inline images, anchored ones as floats, the fallback images of charts and
   SmartArt.
7. **Footnotes, endnotes, hyperlinks, bookmarks and the table of contents field**.
8. **Tracked changes, comments and embedded fonts**, by option.
9. **The conversion report**, the documentation of what is approximated, and the reference comparison.

## Tests required

**Unit** — each mapping on a minimal document that exercises exactly it; style inheritance order; numbering
restarts; merged cells in both directions; header and footer variants; hostile packages (a ZIP bomb, a billion
entries, deep nesting, an external entity, an external relationship) refused and reported, never followed.

**Integration** — the text pdftotext extracts from the converted PDF, in order, against the text of Word's own PDF
of the same document; rasterised pages compared with Word's PDF within the stated threshold; headings and tables
found by PyMuPDF in the same order in both.

## Acceptance conditions

| Documents | Behaviour | Verified by |

| The DOCX that `build_word.ps1` writes for the French invoice, beside `documents/invoice/word-invoice-fr.pdf`, Word's own PDF of it | The converted PDF's text, in order, equals Word's; its pages are within the stated visual threshold of Word's | `CorpusDocxTests.The_invoice_converts_as_word_prints_it` |
| DOCX documents from public sources, with Word's PDF of each (see Corpus) | Text in order, headings and tables found in the same order as in Word's PDF; every approximation reported | `CorpusDocxTests.Word_documents_convert_with_their_structure` |
| Hostile DOCX packages, built by the tests | Refused or bounded, with a diagnostic; no external resource fetched | `DocxHostileInputTests` |

## Corpus

### What the corpus holds

Word's own PDFs of the French invoice — Save as PDF, the Microsoft print driver and PDF24 —, built by
`build_word.ps1` from a DOCX it writes but does not keep; and PDFs from many Word versions among the vendored
documents, without their DOCX sources.

### What it lacks

| Need | Why | Priority | Likely source |
|---|---|---|---|
| A way for non-PDF inputs to enter the corpus | The manifest and its schema accept `.pdf` files only; M7 meets the same wall for image files | 1 | A maintainer decision: the schema, `docs/corpus.md` and the corpus layout extended for source files |
| The DOCX `build_word.ps1` writes, kept beside Word's PDFs of it | The one input whose Word rendering the corpus already holds | 1 | Generated on Windows by `build_word.ps1`, changed to keep the DOCX |
| Business DOCX documents under an open licence — a contract, a letter, a report with numbered clauses — each with Word's PDF | The acceptance needs third-party documents, as every milestone does | 1 | A public source (government templates under open licences) or a contribution |
| DOCX documents with tracked changes, comments, footnotes and embedded fonts | Each option and mapping needs a real case | 2 | Generated here with LibreOffice, and a contribution |

## Traps

- Word's layout is not specified in the document: line and page breaks depend on Word's engine, and the
  acceptance compares text order and structure, with a visual threshold, not positions.
- Numbering in Word is a separate part with its own inheritance; lists that look alike rarely share a definition.
- Theme fonts resolve through the theme part and the language of the run; a missing theme gives Word's defaults.
- A DOCX can reference remote images and templates; following them is an SSRF like any other (ADR 38).
