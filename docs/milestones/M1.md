# M1 — Modèle objet et lecture tolérante

> Statut : en cours — Dépend de : M0

## Objectif

Ouvrir n'importe quel PDF, y compris imparfait, et en résoudre les objets à la demande, sans jamais
charger le document entier en mémoire.

## Périmètre

**Dans le jalon** : modèle objet COS ; lexer et parseur ; filtres de décodage ; toutes les formes de table
de références croisées ; résolution paresseuse ; réparation ; diagnostics.

**Hors jalon, explicitement** : écriture (M2), notion de page (M3), déchiffrement des documents protégés
(M9 — ici on détecte `/Encrypt` et on lève une exception typée), interprétation des flux de contenu (M8).

## Conception

### Modèle objet — `Objects/`

`PdfObject` abstrait, puis `PdfNull`, `PdfBoolean`, `PdfInteger`, `PdfReal`, `PdfName`, `PdfString`,
`PdfArray`, `PdfDictionary`, `PdfStream`, `PdfReference`.

- `PdfName` est interné et comparé par référence ; les noms usuels sont des champs statiques.
- `PdfString` conserve les octets bruts et son mode d'écriture d'origine (littéral ou hexadécimal) ;
  la conversion en texte gère PDFDocEncoding et UTF-16BE avec BOM.
- `PdfStream` porte son dictionnaire et une **source de données paresseuse** : plage du fichier ou mémoire.
  Les données ne sont ni lues ni décodées avant qu'on les demande, et la version encodée reste accessible
  telle quelle — c'est ce qui permettra plus tard de copier un flux d'un document à l'autre sans le recompresser.
- `PdfReference` résout via une source d'objets interne, jamais via un état statique.
- Les accès typés passent par des extensions (`GetDictionary`, `GetArray`, `GetInteger`…) qui **résolvent
  les références au passage** — lire un dictionnaire sans résoudre est le bug classique de ce genre de code.

### Lecture bas niveau — `IO/`

- `PdfLexer` : tokenise sur `ReadOnlySpan<byte>`, sans allouer. Gère les commentaires, les délimiteurs,
  les échappements de chaînes littérales (y compris `\ddd` et les retours ligne échappés), les chaînes
  hexadécimales impaires, les noms avec `#xx`.
- `PdfParser` : construit les objets, avec une **profondeur de récursion bornée** pour les tableaux et
  dictionnaires imbriqués.
- `Filters/` : `FlateDecode` avec prédicteurs PNG et TIFF, `LZWDecode`, `ASCII85Decode`, `ASCIIHexDecode`,
  `RunLengthDecode`, et passage sans décodage pour `DCTDecode`, `JPXDecode`, `CCITTFaxDecode`, `JBIG2Decode`.
  Chaîne de filtres et `DecodeParms` sous forme unique ou de tableau.
- `XRef/` : lecture de la table classique, du flux xref (`/W`, `/Index`), des flux d'objets (`ObjStm`),
  de la chaîne `/Prev`, et des fichiers à référence hybride (`/XRefStm`).
- `PdfFileReader` : orchestre l'indexation, tient le cache LRU borné, expose `GetObject(PdfObjectId)`.

### Réparation

Déclenchée si : `startxref` illisible, offset hors fichier, objet trouvé à l'offset ne portant pas le
numéro attendu, boucle dans la chaîne `/Prev`, ou trailer sans `/Root`. Le balayage cherche les motifs
`N G obj` sur tout le fichier et retient la **dernière** définition de chaque objet, puis le `trailer` ou,
à défaut, un objet `/Type /Catalog`. Chaque réparation produit une entrée de diagnostic.

### Diagnostics — `Diagnostics/`

`PdfDiagnostics` : collection d'entrées `(sévérité, code, message, position)`. Codes stables et documentés,
car ils feront partie du contrat public. Sévérités : information, réparation, avertissement, perte de conformité.

## Découpage en tranches

1. Modèle objet + extensions typées + tests unitaires.
2. Lexer + parseur, sur entrées valides puis malformées.
3. Filtres, avec vecteurs de test connus.
4. Table xref classique + trailer + résolution paresseuse ; ouverture d'un PDF minimal écrit à la main.
5. Flux xref + flux d'objets + chaîne `/Prev` + fichiers hybrides.
6. Réparation par balayage + diagnostics.
7. Durcissement : bornes, corpus hostile, mesure mémoire.

## Tests exigés

- Chaque type d'objet : écriture textuelle canonique, cas limites (chaîne avec parenthèses déséquilibrées,
  nom avec `#`, réel sans partie entière, entier hors bornes `long`).
- Lexer : commentaires, espaces exotiques, fin de fichier prématurée, chaîne hexadécimale impaire.
- Filtres : vecteurs connus pour chacun ; prédicteurs PNG sur données réelles ; chaîne de deux filtres.
- xref : table classique, flux xref, flux d'objets, `/Prev` multiple, fichier hybride, table mensongère.
- Réparation : fichier tronqué, `startxref` faux, xref absente, objet en double.
- Hostilité : `/Prev` circulaire, dictionnaires imbriqués à 10 000 niveaux, `/Length` mensonger,
  `/W` démesuré dans un flux xref, flux annonçant une taille impossible.
- Mémoire : ouvrir un fichier de plusieurs centaines de milliers d'objets sans dépasser un budget fixé.

## Pièges

- Un `/Length` peut être une référence indirecte **et** être faux : il faut savoir retrouver `endstream`.
- Les offsets d'une table xref peuvent être décalés d'un octet ou deux (fichiers produits par des outils
  approximatifs) : chercher l'en-tête d'objet dans une petite fenêtre autour de l'offset avant de conclure.
- Un flux d'objets contient des objets **sans** en-tête `N G obj` : leur position vient de la table de tête.
- Le numéro de génération est presque toujours 0, mais pas toujours ; ne jamais l'ignorer dans les clés.
- Un fichier peut contenir plusieurs `%%EOF` : c'est le signe de mises à jour incrémentales, pas d'une erreur.

## Critères de sortie

- [x] Les fichiers du corpus synthétique s'ouvrent intégralement, cassés compris, avec les diagnostics attendus.
- [x] Aucune entrée malformée ne provoque d'exception non typée, de récursion infinie, ni d'allocation démesurée.
- [x] L'empreinte mémoire à l'ouverture est proportionnelle au **nombre** d'objets, pas à leur taille
      (229 µs et 393 Ko pour un document de 1 000 pages et 4 Mo).
- [x] Les flux ne sont ni lus ni décodés tant qu'ils ne sont pas demandés (vérifié en comptant les lectures).
- [x] Un benchmark d'indexation existe, avec `MemoryDiagnoser`.
- [ ] Un corpus de PDF **réels** complète le corpus synthétique (T03).
- [ ] Le lexer et le parseur sont fuzzés (T08).
- [ ] Un budget mémoire et de débit est vérifié en CI (T09).
