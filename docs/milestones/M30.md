# M30 — Advanced typesetting

> State: to do — Depends on: M12, M28 — Text analysis ours and shaping HarfBuzz's, per [ADR 43](../adr/0043-skia-in-html-and-rendering-and-text-analysis-is-ours.md); PDF/UA-2 output on the PDF 2.0 writer, per [ADR 40](../adr/0040-the-caller-chooses-pdf-1-7-or-2-0-output.md)

## Goal

Typeset what the business target does not need first, but some documents do: vertical text in Chinese, Japanese
and Korean, ruby annotations, and mathematical formulae written in MathML — each laid out correctly, extractable
in reading order, and tagged so that a PDF/UA-2 document carries them accessibly.

## Scope

**In**: CSS Writing Modes — `writing-mode: vertical-rl` and `vertical-lr`, `text-orientation`,
`text-combine-upright`, vertical OpenType features (`vert`, `vrt2`, `vkna`) and vertical metrics (`vhea`, `vmtx`,
or their fallback) — on block and inline layout, pagination and tables; CSS Ruby — `ruby`, `rt`, `rp`,
`ruby-position`, `ruby-align` — with the base and the annotation both extractable; MathML Core layout — tokens,
rows, fractions, radicals, scripts, under and over scripts, tables, stretchy operators from the font's `MATH`
table — painted as text in a math font, and carried into PDF/UA-2 as `Formula` structure elements with the
MathML attached as an associated file.

**Out, explicitly**: LaTeX input (a caller converts it to MathML); MathML presentation beyond MathML Core, and
content MathML; `Tate-chu-yoko` beyond `text-combine-upright`; Mongolian vertical script; vertical text in
existing documents (reading it is M15's).

## Design

- **Writing modes are logical from the start.** M12's layout works in logical inline and block directions; this
  milestone maps them to vertical physical axes rather than adding a second layout. Where M12 assumed horizontal,
  the assumption is removed, with a test.
- **Vertical glyphs** come from the font's vertical features and metrics through HarfBuzz; the ToUnicode map and
  the marked content keep the logical order, so extraction reads top to bottom, right to left.
- **Ruby** lays out as an inline box with an annotation container, tagged `Ruby`, `RB` and `RT` so that assistive
  technology reads both.
- **MathML Core** is laid out with the `MATH` table's constants and glyph variants; a document without a math font
  in the registry reports it and falls back to the embedded OFL math font.

## Slices

1. **Logical layout audit**: every place M12 assumes a horizontal inline axis found and parameterised, with a test
   that rotates a horizontal document's layout to vertical and back unchanged.
2. **Vertical text**: `writing-mode`, `text-orientation`, vertical features and metrics, line breaking in vertical
   lines (UAX #14 with the vertical rules of CSS Text).
3. **Vertical pagination and tables**: pages that fill right to left, tables in vertical flow, margin boxes.
4. **`text-combine-upright`** for numbers within vertical lines.
5. **Ruby**: layout, positions, alignment, tagging, extraction.
6. **MathML Core layout**: tokens, rows, fractions, radicals, scripts, operators, tables, stretchy glyphs from
   the `MATH` table; an embedded OFL math font.
7. **Formula tagging in PDF/UA-2**: `Formula` elements with alternative text and the MathML as an associated file.
8. **Documentation**, and the reference documents.

## Tests required

**Unit** — vertical line breaking on the conformance cases of the specifications; logical order kept in marked
content; ruby boxes and their tags; MathML layout of each element against reference geometry; fallback to the
embedded math font with a diagnostic; hostile MathML (deep nesting, huge tables) bounded.

**Integration** — veraPDF's PDF/UA-2 profile on the reference documents; text extracted by pdftotext and PyMuPDF
in reading order; rasterised pages compared with Chromium's rendering of the same HTML, which supports vertical
writing, ruby and MathML Core.

## Traps

- A layout written for horizontal text hides its assumption in dozens of places; the audit comes first.
- Vertical metrics are often missing from fonts; the fallback must be the one CSS specifies, not a guess.
- Extraction order and visual order diverge in vertical text more than anywhere else: marked content must say
  the logical order.
- MathML inside HTML arrives through AngleSharp's parser, which handles its namespace; its layout is ours.
