# M23 — Optimisation, performance, hardening

> State: to do — Depends on: M12, M15, M22 — Guards classified per [ADR 34](../adr/0034-every-valid-pdf-is-readable-and-the-readers-guards-are.md); native memory only where a measurement asks for it, per [ADR 35](../adr/0035-unsafe-code-where-a-measurement-asks-for-it.md); lossy steps opt-in and reported, JBIG2 lossless only, per [ADR 42](../adr/0042-image-codecs-and-scans.md)

## Goal

Deliver the frugality the library promises, with numbers: budgets for time and allocation enforced in CI, a
decode that holds a piece of a stream rather than all of it, caches with a budget, files made smaller without
changing what they say, and a core proved to run under Native AOT, trimming and browser WebAssembly and in a
constrained container.

Every milestone before this one measures what it adds. This one turns the measurements into budgets that fail the
build, pays the debts the earlier milestones deferred here — T07, T09, T22, T24, T28, T30, T33 — and adds the
operations whose only purpose is size: deduplication, recompression, downsampling, linearisation.

## Scope

**In**: performance budgets in CI; the debts named above; global resource deduplication and consolidation of
duplicate font subsets; subsetting of inherited fonts; lossless recompression and linearisation; image
downsampling and re-encoding with a target-size mode, every lossy step opt-in and reported (ADR 42); Native AOT,
trimming and browser WebAssembly validation of the core; a measured container profile beside a Chromium
baseline; fuzzing campaigns over the lexer, the parser and the M22 decoders; the `optimise` verb of the tool.

**Out, explicitly**: mixed raster content compression (an open question of the roadmap); rasterisation (M25);
anything that changes what a document says — an optimisation that alters extracted text or a conformance claim
fails, it is never reported as a trade-off.

## Design

```
PdfOptimizer                 plans, then applies, a set of optimisations; each is lossless unless named lossy
PdfOptimizerOptions          immutable: which steps, the lossy ones opted into by name, a target size
PdfOptimizationReport        what each step saved, what it changed, and every lossy change with its image
IStreamDecodeSink            receives a decoded stream a window at a time (T28)
```

- **Lossless first.** Deduplication by content hash of streams and of dictionaries after their references are
  resolved; duplicate font subsets from merged documents consolidated when their glyph sets can be unioned;
  Flate at a stronger level; object and cross-reference streams; unreferenced objects dropped (M7 prunes
  resources per page; this prunes per document).
- **Lossy only by name.** Downsampling above a resolution, JPEG re-encoding at a quality, conversion to one bit
  per pixel; each listed in the report with the image, its page, its old and new size and resolution. The
  target-size mode applies the named steps in order until the file fits, and says if it cannot.
- **Streaming decode.** A stream is decoded into a sink a window at a time; `MaxDecodedStreamLength` then bounds
  what is held at once, and a stream past `Array.MaxLength` is read whole under `PdfReaderLimits.Unbounded`
  (T28). Native memory is used only if a benchmark shows the managed path cannot meet its budget (ADR 35).
- **Budgets.** Each budget is a BenchmarkDotNet result compared with a committed baseline and a tolerance; CI
  runs the budget benchmarks with a fixed job on every pull request and fails beyond the tolerance.

## Slices

1. **Budgets in CI.** The reader, validation and writer benchmarks gain committed baselines; a CI job runs them
   with a fixed short job and fails when allocation exceeds its budget (T09 for throughput). Proven by a test that
   a deliberately allocating change fails the job.
2. **The object cache.** LRU in place of FIFO, names interned without an intermediate string (T07), measured.
3. **Decoded object streams under a budget** (T33): the cache of decoded object streams evicts beyond a byte
   budget, and an evicted stream decodes again when asked. The damaged file of four 256 MB object streams holds
   the budget.
4. **Windows grown on demand** for cross-reference sections (T24) and the rebuild's trailer scan (T30); the two
   documents recorded as unsupported for T24 become supported, and the 80,000-keyword file costs a bounded read
   per keyword.
5. **Streaming decode** (T28): the filter pipeline writes to a sink; the USGS topographic map decodes its
   328 MB image under a 64 MB hold, and a synthetic stream decoding past 2 GB is read whole under `Unbounded`.
6. **Lossless optimisation**: deduplication, font subset consolidation, inherited-font subsetting, recompression,
   object streams, unreferenced objects; the report of what each saved.
7. **Linearisation**, written and verified by qpdf's `--check-linearization`.
8. **Lossy image steps** on the M22 codecs, and the target-size mode; the report of every lossy change.
9. **Native AOT, trimming and WebAssembly**: an AOT executable opens, transforms and writes every corpus
   document; the core's trimming warnings are zero; a browser-wasm host runs the same operations.
10. **The container profile**: a chiseled image without fontconfig, a read-only file system and a 512 MB cap,
    measured on the reference documents beside headless Chromium in the same limits.
11. **Fuzzing campaigns**: the nightly campaign extended to the writer's round trip and to the M22 decoders,
    seeded with the damaged corpus.
12. **The `optimise` verb**, and the documentation.

## Tests required

**Unit** — each optimisation alone on a document that needs exactly it, and on one that does not (no change);
deduplication never merges two objects that differ after resolution; a lossy step never runs unless named; the
target-size mode stops and reports when the target cannot be met; the cache evicts in LRU order and a re-decoded
object stream yields identical objects; the streaming decode yields the same bytes as the whole decode, window
boundary by window boundary, for every filter and predictor.

**Integration** — qpdf `--check` and `--check-linearization` on every optimised document; the text pdftotext
extracts before and after lossless optimisation is identical; veraPDF upholds the same conformance claims before
and after; the container profile measured in CI's container runner beside a Chromium container.

## Corpus

### What the corpus holds

The stress documents: ReportLab's thousand-page journal, committed, and W11's three remote references (9,302
pages, one 63 MB page, a 147 MB JPEG 2000 scan). The damaged documents, the fuzzing seeds. The scans in CCITT,
JPEG and JPEG 2000, from the OPF format corpus and the remote corpus. The T24 documents, remote.

### What it lacks

| Need | Why | Priority | Likely source |
|---|---|---|---|
| A stream that decodes past 2 GB | The `Unbounded` acceptance needs one; no real file in the corpus reaches it | 1 | Generated at test time by a synthetic writer, never committed |
| A colour scan too large for a court portal's cap | Proves the target-size mode on the case the feature exists for | 2 | A contribution (a copier scan), or the remote corpus |
| A case file merged from many producers' documents, each with its own subsets of the same fonts | Measures font subset consolidation on real subsets | 2 | Generated here: LibreOffice and Chromium documents merged by qpdf |
| Chromium's footprint for the reference documents in the container profile | The baseline the container comparison needs | 2 | Generated here, in CI, by the comparison benchmarks' Chromium slot |

## Traps

- An optimisation that changes what a document says is a corruption, not a trade-off: extracted text and
  conformance are the acceptance, not only size.
- Deduplication must compare objects after their references resolve, and never across encryption contexts.
- A budget that is too tight trains contributors to raise it; set each from measurements with a stated
  tolerance, and record every raise in `docs/status.md` with its reason.
- Shared CI runners are noisy: allocation budgets are reliable, time budgets need a tolerance and a fixed job.
- Linearised output must stay linearised after an incremental update, or say that it no longer is.
